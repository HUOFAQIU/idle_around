> 类型：实现 | 状态：有效 | 核对：2026-11-01
> 何时读：排查战斗、魂灵、触发器、状态效果；新增调试事件；理解 DebugWindow 的数据来源
> 关键词：调试 DebugWindow 遥测 CombatTelemetry 事件 trace 因果链 SoulRuntime 快照 导出 JSONL
> 代码：`Scripts/debug/`、`game/battle/soul_runtime.gd`、`game/battle/soul_runtime_db.gd`、`Windows/Debug/`、`Scripts/test_api.gd`
> 相关：`指南/调试窗口.md`、`架构/战斗运行时_施法与冷却.md`、`架构/GAS.md`

## 1. 设计目标

战斗是自动化的，靠看画面很难判断“这颗魂灵为什么没放、触发器为什么没触发、状态是谁施加的”。遥测层解决三件事：

1. **事件化**：施法、选目标、效果施加、状态、周期 tick、触发器、充能、死亡、掉落都变成带时间戳的事件；
2. **可追溯**：一次施法派生出的效果/触发/充能共享一条 `trace`，能还原因果链；
3. **不侵入**：事件记录不参与战斗判定；关掉 `CombatTelemetry.enabled` 后 `record()` 立即返回。

## 2. 组成

```
BattleUnit / AutoCastAbility / ChargedAbility / BattleManager
        │  record(category, type, fields)
        ▼
CombatTelemetry (Autoload)
        ├─ 环形事件缓冲 events
        ├─ event_recorded 信号 ──────────────► DebugWindow 时间线
        ├─ 可选 JSONL 文件 (user://debug)
        └─ query / get_trace_chain / export_jsonl

BattleUnit.add_soul_abilities()
        │ 逐颗魂灵建 SoulRuntime
        ▼
SoulRuntimeDB (Autoload)
        ├─ 玩家已装备 SoulData 实例 → SoulRuntime
        ├─ runtime_registered / runtime_unregistered ─► ItemView 绑定/解绑
        └─ player_runtimes() / all() ─────────────────► DebugWindow 总览/魂灵页
           （怪物魂灵不注册：可能多只怪共享同一份 SoulData；快照读 BattleUnit.loadout）
```

关键原则：

- 事件里**不存 Node 引用**；`CombatEvent.unit_info()` 在入口把单位转成 `{id, name, team}`。
- `SoulData` 只放静态数据；扫描线、加速/减速/冻结、统计都在 `SoulRuntime`。
- 不修改 `addons/GodotGAS`；项目侧通过 `SoulEffectContext`（`GameplayEffectContext` 子类）携带 trace。

## 3. 事件模型

统一字段：

| 字段 | 说明 |
|---|---|
| `seq` | 全局自增序号 |
| `run_id` | 战斗场次；`BattleWindow._run_id` |
| `frame` | 进程帧 |
| `t` | 战斗内秒数 |
| `category` | `battle / cast / soul / trigger / effect / attribute / tag / log / system` |
| `type` | 事件类型，调试窗口负责翻译成中文 |
| `importance` | `important`（全局记录）或 `detail`（只记录关注单位） |
| `actor` / `target` / `unit` | `{id, name, team}`，由 `actor_unit` 等转换 |
| `soul` / `ability` / `ability_tag` / `effect` | 魂灵/技能/效果标识 |
| `amount` / `health_delta` / `shield_delta` / `burn_delta` | 数值 |
| `trace_id` / `parent_trace_id` / `root_trace_id` | 因果链 |
| `detail` | 人类可读补充 |
| `color` | 时间线颜色 |

重要度规则：

- 玩家相关（玩家施法、玩家受击、玩家状态、玩家死亡）→ `important`；
- 敌人细节（敌人属性变化、周期 tick、移动、充能）→ `detail`；
- `detail` 只有 `watch_unit_id` 指向的单位或 `record_detail_globally = true` 才入缓冲，避免无限刷怪冲爆缓冲。

## 4. 因果链

`CombatTrace` 只保存 id / parent_id / root_id / cause：

```
cast:温泉 (trace 1)
├─ soul used
├─ Event.Combat.SoulUsed → trigger:其他魂灵被使用 (trace 2) → 冰车 charge
├─ effect 灼烧 (trace 1)
└─ periodic tick (trace 1)
```

`AutoCastAbility` 从 `try_activate()` 的 payload 读取父 trace；每次施法创建 `cast:<技能名>`。效果 spec 用 `SoulEffectContext` 携带 trace；触发器、充能、周期 tick 继承父 trace。`CombatTelemetry.get_trace_chain(trace_id)` 返回同一 root 下的事件。

## 5. 接入点

| 文件 | 记录内容 |
|---|---|
| `BattleManager` | 开战/结束、单位入场、跨格移动、进入/离开攻击范围、掉落、原始日志镜像 |
| `BattleUnit` | 触发器 fired、效果施加、冻结广播、魂灵 used、运行时 loadout |
| `ChargedAbility` | 冷却完成、外部充能、加速/减速/冻结施加与到期 |
| `AutoCastAbility` | 施法尝试/激活/空放/选目标/吟唱/暴击/投射物/效果结算 |
| `BattleBrain` | 触发器充能入队、flush 拒绝 |
| GAS ASC 信号 | 属性变化、标签增删/层数、ActiveEffect 增删、周期 tick、能力授予/失败、GameplayEvent |
| `BattleWindow` | `begin_run` / `end_run`、loadout 快照、关注玩家 |

## 6. 性能约定

- 不记录每帧充能；只记录外部充能、状态、激活、触发。
- 移动只在跨格时记录，且是 `detail`。
- 敌人默认只记录重要事件；玩家和关注单位才记录详细事件。
- 环形缓冲默认 5000 条；`max_events` 可调。溢出不报错，只累计 `dropped_events`。
- DebugWindow 只在自己可见时轮询快照，界面刷新 10Hz、树列表 2Hz；关闭时不轮询。
- 字符串/JSON 格式化只在 UI 或导出时做，记录路径只存原始字段。

## 7. 新增一个调试事件

1. 在 `Scripts/debug/combat_event.gd` 选定 `category`（没有合适的再加常量）；
2. 在触发点调用：
   ```gdscript
   CombatTelemetry.record(CombatEvent.CAST, "your_event", {
       "actor_unit": caster,
       "target_unit": target,
       "soul": soul_name,
       "effect": effect_name,
       "amount": value,
       "trace": trace,
       "detail": "人类可读说明",
   }, CombatEvent.IMPORTANT)
   ```
3. 需要详细事件时用 `CombatEvent.DETAIL`，并确保关注单位能覆盖；
4. 在 `Windows/Debug/debug_window.gd` 的 `TYPE_NAMES` 加中文名（没有会显示英文 type）；
5. 更新本文件的接入点表格。

不要在这里写战斗判定；需要“为什么没放”时，记录原因字符串即可。
