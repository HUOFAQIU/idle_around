## 1. 设计原则

- **单槽**：`user://saves/slot_0.json`；以后加多槽只改文件名，格式不变。
- **只存玩家做了什么**：容器里的物品（`content_id` + 左上角格）、见闻已解锁、`saved_at_unix`、`play_time_sec`。魂灵冷却、HP、怪物、扫描线、`SoulRuntime` 等战斗运行期状态一律不存，读档后从新一场开始。
- **静态数据不进存档**：不存资源路径、不存 `ItemData` 的静态字段；读档按 ID 从 `CollectionDB` 重建。改魂灵数值、改图标、改技能都不需要迁移存档。
- **玩家数据用 JSON**：不把 `ResourceSaver` 写出的 Resource 放进 `user://` 再 `load()`。JSON 可读、可手改排查，也不会因为脚本类变化而整份存档打不开。
- **不存场景配置**：容器尺寸、`avilable_types`、`equip_part` 由场景/代码决定，旧存档不能反向覆盖新配置。
- **不依赖 GBIS 自带存档**：`GBIS.save()` 写 `res://Saves/` 且序列化整个仓库；游戏层只用 `ContainerData` 的公开读写接口。

## 2. 文件结构

```json
{
  "version": 1,
  "saved_at_unix": 1793923200,
  "play_time_sec": 3721.5,
  "containers": {
	"inventory_0": [
	  { "kind": "soul", "id": "xiao_lu_soul", "name": "小鹿", "at": [0, 0] },
	  { "kind": "soul", "id": "du_ya_soul", "name": "毒牙", "at": [5, 0] }
	],
	"cell_2": [
	  { "kind": "soul", "id": "kong_lang_soul", "name": "恐狼", "at": [0, 0] }
	]
  },
  "detached": [
	{ "kind": "soul", "id": "mian_bao_soul", "name": "面包" }
  ],
  "collection": {
	"monsters": ["snake_data"],
	"souls": ["xiao_lu_soul"]
  }
}
```

- `at` 是物品左上角格，形状从资源本身读；`name` 只用于 ID 改名后的兜底和排查，不是读取依据。
- `detached` 是保存瞬间正在鼠标上的物品；读档时放回仓库第一个空位（`Warehouse.add_item()`），避免丢失。
- 空容器不写入 `containers`；读档时所有 `GBIS.inventory_names` 里的容器先清空，再按文件重建。商店、装备槽不存。
- 因 mod 缺失/容器满而暂时放不进世界的记录额外写到 `orphaned`：`[{"container": "inventory_0", "record": {...}}]`；没有就不写。
- 写入时 `JSON.stringify(data, "\t")` 排序键，容器记录按锚点排序，见闻 ID 按字母排序，方便 diff。

## 3. 保存时机

| 触发 | 行为 |
|---|---|
| 背包物品增删改、`sig_inv_refresh` | `mark_dirty()`，去抖 2 秒后写盘 |
| 见闻解锁 `entry_unlocked` | `mark_dirty(true)`，下一帧写盘（低频、不可再生） |
| 运行中 | 每 30 秒心跳写一次，刷新 `saved_at` / `play_time` |
| 关闭主窗口 / 应用暂停 | `NOTIFICATION_WM_CLOSE_REQUEST` / `NOTIFICATION_APPLICATION_PAUSED` 同步写 |
| 测试 / 手动 | `SaveManager.save_now()`、`TestAPI.save_now()` |

`SaveManager._process()` 统一负责去抖和心跳；不要在信号回调里直接写文件。战斗掉落可能一秒一次，逐次写盘没有必要。

## 4. 读档流程

`SaveManager` 在 autoload 里排在 `CollectionDB`、`SoulRuntimeDB`、`Warehouse` 之后。`_ready()` 先 `await get_tree().process_frame`：`Warehouse` 预注册 `inventory_0..inventory_9`，各窗口的 `InventoryView._ready()` 再注册 `cell_0..3`，等容器都进 GBIS 后执行 `load_game()`。`--script`/工具模式没有主场景，等完一帧如果 `get_tree().current_scene == null` 就直接返回，不读也不写；否则容器不齐时读档会跳过物品，之后自动写档可能丢物品。

```text
读主文件 → 失败读 .bak → 再失败当作新游戏
清空所有 GBIS.inventory_names 容器
按容器、按 at.y / at.x 排序：
	kind + id → CollectionDB 取模板 → duplicate()
	try_add_to_grid(锚点) 成功 → 继续
	失败 → add_item() 放第一个空位
	仍失败 → Warehouse.add_item() 转仓库其他空位
	仍失败 → 跳过并 warning
detached → Warehouse.add_item() 放仓库第一个空位
应用 collection；没有该段时尝试旧 user://collection.cfg
emit sig_inv_refresh 一次
```

- 不能用 `GBIS.add_item()` 读档：它只找第一个空位，会破坏魂灵左右相邻关系。先 `try_add_to_grid()` 保精确列，失败才兜底。
- 直接操作 `ContainerData` 不逐件发信号，最后发一次 `sig_inv_refresh` 让所有 `InventoryView` 重建。
- 新游戏、从备份恢复、版本迁移后会自动写回一次。

## 5. 物品编码规则

- 魂灵：`kind = "soul"`，`id` 优先用 `SoulData.content_id`（core 和 mod 都由 manifest 写入）；没有才按 `item_name` 反查。
- `content_id` 随 `duplicate()` 进入背包副本，所以 mod 内容即使和原版/其他 mod 显示名相同也不会串档。
- 背包里的物品是 `GBIS.add_item()` 复制出来的副本，没有 `resource_path`，旧资源只能靠 `item_name` 兜底。
- 读档先按 ID 查；查不到再按记录里的 `name` 查一次，兼容资源改名但没有加 alias 的情况。仍查不到就跳过该物品并 `push_warning`。
- 旧 ID 映射沿用 `CollectionDB.LEGACY_SOUL_ID_ALIASES`（例如 `du_ya_soul_2 → du_ya_soul`），读档时统一成 canonical ID。
- 新增物品类型时在 `SaveCodec` 加 `kind` 分支，确保能按 ID 找回原资源；不要往存档里塞整份 Resource。

## 6. 见闻

`CollectionDB` 不再自己写 `user://collection.cfg`：

- `to_save_data()` / `apply_save_data()` 负责序列化和恢复；`apply_save_data()` / `load_legacy_state()` 结束后发 `state_reloaded`，见闻窗口据此整体刷新；
- 解锁时只发 `entry_unlocked`，由 `SaveManager` 标记立即写盘；
- 首次加载统一存档时如果文件里没有 `collection` 段，会调用 `load_legacy_state()` 只读导入旧 `collection.cfg`，随后写进新存档；旧文件保留，不删除。

## 7. 版本、备份与损坏恢复

- `version` 目前是 `1`。以后结构变化在 `_migrate()` 里按版本逐级迁移，迁移后写回。
- 主文件版本高于当前游戏时只读、不覆盖原文件，避免旧客户端破坏新存档。
- 写盘：先写 `slot_0.json.tmp`，把旧主文件轮换成 `slot_0.json.bak`，再把临时文件改名为主文件。写临时文件失败不会动旧存档。
- 读盘：主文件不存在或 JSON 解析失败时读 `.bak`；从备份恢复后的第一次写盘会保留那份好备份（`_keep_backup_next_save`）。
- 备份中仍找不到的 ID、放不下的物品：不丢弃，写进 `orphaned` 并写 warning；写档时原样带回，重新启用 mod 后再读档会尝试放回原容器/仓库。
- `orphaned` 是附加段；旧存档没有它按空数组处理，`version` 仍为 1。

## 8. 已知边界

- 单槽；没有主菜单/新游戏按钮，启动自动读档。删档用 `TestAPI.delete_save()` 后再 `load_save()`。
- 当前可持久化的物品只有 `SoulData`（`kind = "soul"`）；以后加入其他物品类型时在 `SaveCodec` 补 kind 分支。
- 容器名（`inventory_0..inventory_9`、`cell_0..3`）变化视为不兼容：旧存档里找不到的容器会 warning 并跳过；需要保留进度时在迁移函数里改名。`--script`/工具模式会在读档前直接返回，不会触发这个跳过逻辑。
- 仓库 10 页各自是独立容器；空页不写入 `containers`，旧存档里的 `inventory_0` 自然成为第 1 页，其余页为空。
- 读档只保证在非战斗、非拖拽状态安全；自动读档在启动时，手动读档不要在战斗中调用。
- 战斗状态不持久化：关掉游戏再开，从一场新的空战斗开始。
- 窗口位置、音量等全局设置还没有接入；以后放独立的 `user://settings.cfg`，不随新游戏重置。
- 离线收益还没有实现；`saved_at_unix` 已经写进存档，后续做挂机结算只依赖这个时间戳，不存战斗快照。

## 9. 测试

`TestAPI` 已暴露：`save_now()`、`load_save()`、`delete_save()`、`has_save()`、`get_save_path()`、`dump_save()`。最小回归：

1. 在 `inventory_0` 和 `cell_0..3` 的指定格放魂灵；
2. `save_now()` → 清空容器 → `load_save()`；
3. 断言每个物品的 ID 和左上角格完全一致；
4. 再存一次生成 `.bak`，把主文件写坏，`load_save()` 应从备份恢复；
5. 断开一个魂灵 ID 再读，确认只跳过坏条目、其余正常。
