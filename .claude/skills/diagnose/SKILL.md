# 先建反馈环，再下结论

没有一条能变红、也能变绿的命令，不提根因。猜三次不如跑一次。

规则来源：症状路由见 `DOC/INDEX.md`；文档回写规范见 `DOC/指南/文档规范.md` §3；情景测试写法见 `DOC/指南/代码检查.md`「情景测试」；TestAPI 用法见 `DOC/指南/AI测试接口.md`。

## 1. 选反馈环

按症状落在哪一层选，从上往下取第一个能用的：

| 层 | 环 | 命令 |
|---|---|---|
| 领域行为（存档、战斗、地图、开局） | 已有情景用例，或新写一个 | `bash tools/check.sh --scenario <名>` |
| 窗口、交互、数据可见性 | `TestAPI` 驱动 + 快照断言，无头跑 | 见 `DOC/指南/AI测试接口.md` |
| 视觉、帧表现 | 钉死参数后读主视口像素 | `DOC/指南/特效与Cue.md` §六 |
| 引擎、编辑器行为 | 最小复现场景，手动一步操作 | 独立 `.tscn` 或探针 |

- 新写情景：在 `tools/scenarios/cases/` 建脚本，`extends ScenarioCase`，实现 `case_name()` / `run(ctx)`，再注册进 `run.gd` 的 `CASES`。
- 无头运行必须隔离 `user://`：`tools/check.sh` 已处理；手工起 Godot 时把 `APPDATA` / `XDG_DATA_HOME` 指到临时目录，别写真实存档。
- 临时探针：只放首方目录，不碰 `addons/`；跑完拆掉，报告「探针已拆、git diff 干净」。

先确认环是红的：它必须因为报告的症状而失败，而不是因为写法错。

## 2. 路由到已知检查点

`DOC/INDEX.md` 路由表 → 目标文档的「常见排查」→ 再 grep 代码。不要从头读实现文档。

高频入口：

- 存档：`DOC/指南/存档排查.md`
- 战斗不放技能 / 不触发 / 没伤害 / Cue 不播：`DOC/指南/调试窗口.md`
- mod 未生效 / 内容缺失 / orphaned：`DOC/架构/Mod系统.md` §11
- 窗口与场景：`DOC/架构/窗口与场景.md` §3
- 特效不显示：`DOC/指南/特效与Cue.md` §五、§六

## 3. 收敛

- 一次只改一个变量。每个假设先写下「如果成立，环上应该看到什么」，跑完对照。
- 先看数据再看渲染：数据层对了，是表现问题；数据层不对，往上游追一层。
- 方向不明时二分：屏蔽一半输入或一半代码路径，看环是否变化。

## 4. 修复与回写

- 修复必须让同一个环由红转绿，不许换一个更容易过的环。
- 把「症状 → 检查点 → 结论」写进对应文档的「常见排查」；跨主题的坑写进 `DOC/架构/现状与注意.md`。
- 改动触发 `DOC/spec/README.md` 的写 spec 条件时，先出 spec 再动手。
- 收尾跑 `bash tools/check.sh --all`。

## 5. 汇报

按「现象 / 变红的命令与输出 / 根因 / 修复 / 验证结果 / 回写了哪节文档」六行汇报，附 `file:line`。没找到根因就直说，列出已排除的假设和下一步要测的东西。
