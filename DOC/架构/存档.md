## 1. 设计原则

- **单槽**：`user://saves/slot_0.json`；以后加多槽只改文件名，格式不变。
- **只存玩家做了什么**：容器里的物品（`content_id` + 左上角格）、魂器内部的魂灵、见闻已解锁（怪物/魂灵/魂器）、`saved_at_unix`、`play_time_sec`。魂灵冷却、HP、怪物、扫描线、`SoulRuntime` 等战斗运行期状态一律不存，读档后从新一场开始。
- **静态数据不进存档**：不存资源路径、不存 `ItemData` 的静态字段；读档按 ID 从 `CollectionDB` 重建。改魂灵数值、改图标、改技能都不需要迁移存档。
- **玩家数据用 JSON**：不把 `ResourceSaver` 写出的 Resource 放进 `user://` 再 `load()`。JSON 可读、可手改排查，也不会因为脚本类变化而整份存档打不开。
- **不存场景配置**：容器尺寸、`avilable_types`、`vessel_kind`、`max_items` 由场景/代码决定，旧存档不能反向覆盖新配置。
- **不依赖 GBIS 自带存档**：`GBIS.save()` 写 `res://Saves/` 且序列化整个仓库；游戏层只用 `ContainerData` 的公开读写接口。
- **职责分层**：`SaveManager` 只是门面；磁盘 IO 在 `SaveStorage`，去抖/心跳在 `SaveScheduler`，顶层 schema/版本/迁移在 `SaveDocument`，各数据域实现 `SaveParticipant`。加新持久化域不要再往 SaveManager 里堆字段。

## 2. 组成与文件结构

```text
SaveManager（Autoload 门面）
├─ SaveStorage                 磁盘读写 / 备份轮换 / 只读态
├─ SaveScheduler               脏标记 / 2 秒去抖 / 30 秒心跳
├─ SaveDocument                顶层 schema / 版本 / 迁移
└─ participants（按注册顺序 collect / apply）
   ├─ ContainerSaveParticipant   容器 + detached + orphaned
   └─ CollectionSaveParticipant  见闻
```

```json
{
  "version": 1,
  "saved_at_unix": 1793923200,
  "play_time_sec": 3721.5,
  "containers": {
	"inventory_0": [
	  { "kind": "soul", "id": "xiao_lu_soul", "name": "小鹿", "at": [0, 0] },
	  { "kind": "soul", "id": "du_ya_soul", "name": "毒牙", "at": [5, 0] }
	],
	"vessel_cell_0": [
	  {
		"kind": "vessel", "id": "mei_you_deng_vessel", "name": "煤油灯", "at": [0, 0],
		"contents": [
		  { "kind": "soul", "id": "kong_lang_soul", "name": "恐狼", "at": [0, 0] }
		]
	  }
	]
  },
  "detached": [
	{ "kind": "soul", "id": "mian_bao_soul", "name": "面包" }
  ],
  "collection": {
	"monsters": ["snake_monster"],
	"souls": ["xiao_lu_soul"],
	"vessels": ["mei_you_deng_vessel"]
  }
}
```

- `at` 是物品左上角格，形状从资源本身读；`name` 只用于排查，不是读取依据，读档只认 `id`。
- 魂器记录额外带 `contents`：数组格式与容器记录相同，锚点相对魂器内部容器。读档时先按 ID 复制魂器实例，再把内部魂灵放回；魂器内部容器名不存档。
- `detached` 是保存瞬间正在鼠标上的物品；读档时放回仓库第一个空位（`Warehouse.add_item()`），避免丢失。
- 空容器不写入 `containers`；读档时期望容器（仓库页 + 魂器槽）先清空，再按文件重建。商店、装备槽不存。
- 因 mod 缺失/容器满而暂时放不进世界的记录额外写到 `orphaned`：`[{"container": "inventory_0", "record": {...}}]`；没有就不写。
- 写入时 `JSON.stringify(data, "\t")` 排序键，容器记录按锚点排序，见闻 ID 按字母排序，方便 diff。

## 3. 保存时机

| 触发 | 行为 |
|---|---|
| 背包物品增删改、`sig_inv_refresh` | `mark_dirty()`，去抖 2 秒后写盘 |
| 见闻解锁 `entry_unlocked` | `mark_dirty(true)`，下一帧写盘（低频、不可再生） |
| 运行中 | 每 30 秒心跳写一次，刷新 `saved_at` / `play_time` |
| 关闭主窗口 / 应用暂停 | `NOTIFICATION_WM_CLOSE_REQUEST` / `NOTIFICATION_APPLICATION_PAUSED` 同步写 |
| 测试 / 手动 | `SaveManager.save_now()`、`TestAPI.save_now()` |

`SaveManager._process()` 每帧把 delta 交给 `SaveScheduler`；去抖/心跳阈值都在 scheduler 里。不要在信号回调里直接写文件。战斗掉落可能一秒一次，逐次写盘没有必要。

## 4. 读档流程

`SaveManager` 在 autoload 里排在 `CollectionDB`、`SoulRuntimeDB`、`Warehouse` 之后。`_ready()` 先 `await get_tree().process_frame`：`Warehouse` 预注册 `inventory_0..inventory_9`，`CharacterWindow` 里的 `InventoryView._ready()` 再注册 `vessel_cell_0..2`。读档前检查“期望容器集合”（仓库各页 + 三个魂器槽）是否全部注册：

- 没有主场景（`--script`/工具模式）：只读，不读也不写；
- 主场景存在但缺容器：只读并报错，列出缺失容器名，避免未恢复的容器随后被空数据覆盖；
- 全部就绪：执行 `load_game()`。

`TestAPI.get_save_status()` 可查看 `ready` / `read_only` / `missing_containers`。

读档时会依次调用 participant 的 `apply_from()`（容器 → 见闻，顺序由 `SaveManager._ready()` 的注册顺序决定），再调用 `finish_load()` 重试孤儿物品；任一环节返回 `true` 都会在最后回写一次。

```text
读主文件 → 失败读 .bak → 再失败当作新游戏
清空期望容器集合（仓库各页 + 三个魂器槽）
按容器、按 at.y / at.x 排序：
	kind + id → CollectionDB 取模板 → make_instance()
	魂器：先重建空容器，再按 contents 记录放回内部魂灵
	try_add_to_grid(锚点) 成功 → 继续
	失败 → add_item() 放第一个空位
	仍失败 → Warehouse.add_item() 转仓库其他空位
	仍失败 → 跳过并 warning
detached → Warehouse.add_item() 放仓库第一个空位
应用 collection；没有该段时按空状态
emit sig_inv_refresh 一次
```

- 不能用 `GBIS.add_item()` 读档：它只找第一个空位，会破坏魂灵左右相邻关系。先 `try_add_to_grid()` 保精确列，失败才兜底。
- 直接操作 `ContainerData` 不逐件发信号，最后发一次 `sig_inv_refresh` 让所有容器视图置脏，可见时再重建。例外是物品放不下时经 `Warehouse.add_item()` 转仓库，这条路径会发 `sig_inv_item_added`。
- `CollectionDB` 在 `_ready()` 就建立 `_seen` 的两个种类桶，`_mark_seen()` 对缺失桶自愈；因此上面那条转仓库路径即使发生在 `apply_save_data()` 之前，魂灵解锁也能正常记录。
- 存档里出现当前未注册的容器时，原始记录逐条转入 `orphaned`，下次写档继续保留，不再直接丢弃。
- 新游戏、从备份恢复、版本迁移后会自动写回一次。

### 4.1 新增持久化域

1. 新建 `XxxSaveParticipant extends SaveParticipant`，实现 `collect_into(document)` 与 `apply_from(document, has_disk_data)`；需要等所有 participant 恢复完再处理的逻辑（例如物品重试入包）放 `finish_load()`。
2. 顶层 section 键加到 `SaveDocument`；如果结构变化需要迁移，在 `SaveDocument.migrate()` 里按版本处理。
3. 在 `SaveManager._ready()` 的 `_participants` 按读档依赖顺序注册。
4. 同步更新本文档；需要测试入口时在 `Scripts/test_api.gd` 补方法。

## 5. 物品编码规则

- 魂灵：`kind = "soul"`，`id` 直接用 `ItemData.content_id`（core 和 mod 都由 manifest 写入）。
- 魂器：`kind = "vessel"`，除 `id` 外带 `contents`（内部魂灵记录数组，锚点相对内部容器）。`CollectionDB.get_vessel(id)` 找不到时整件魂器进 `orphaned`；内部某颗魂灵找不到时只保留那条魂灵记录，魂器其余内容正常恢复。
- `content_id` 随 `duplicate()` / `make_instance()` 进入背包副本，所以 mod 内容即使和原版/其他 mod 显示名相同也不会串档。
- 背包里的物品是 `GBIS.add_item()` 复制出来的副本，没有 `resource_path`；`content_id` 随复制保留，读档不需要按名字反查。
- 读档只按 `id` 查；查不到就跳过该物品并 `push_warning`，不会回退到 `name`。
- 新增物品类型时在 `SaveCodec` 加 `kind` 分支，确保能按 ID 找回原资源；不要往存档里塞整份 Resource。

## 6. 见闻

`CollectionDB` 的见闻状态由 `SaveManager` 统一管理：

- `to_save_data()` / `apply_save_data()` 负责序列化和恢复；`apply_save_data()` 结束后发 `state_reloaded`，见闻窗口据此整体刷新；
- 解锁时只发 `entry_unlocked`，由 `SaveManager` 标记立即写盘；
- 存档里没有 `collection` 段时按空状态处理。

## 7. 版本、备份与损坏恢复

- `version` 目前是 `1`。以后结构变化在 `SaveDocument.migrate()` 里按版本逐级迁移，迁移后写回。
- 主文件版本高于当前游戏时只读、不覆盖原文件，避免旧客户端破坏新存档。
- 写盘：先写 `slot_0.json.tmp`，把旧主文件轮换成 `slot_0.json.bak`，再把临时文件改名为主文件。写临时文件失败不会动旧存档。
- 读盘：主文件不存在或 JSON 解析失败时读 `.bak`；从备份恢复后的第一次写盘会保留那份好备份（`_keep_backup_next_save`）。
- 备份中仍找不到的 ID、放不下的物品：不丢弃，写进 `orphaned` 并写 warning；写档时原样带回，重新启用 mod 后再读档会尝试放回原容器/仓库。
- `orphaned` 是附加段；没有该段时按空数组处理，`version` 仍为 1。

## 8. 已知边界

- 单槽；没有主菜单/新游戏按钮，启动自动读档。删档用 `TestAPI.delete_save()` 后再 `load_save()`。
- 当前可持久化的物品有 `SoulData`（`kind = "soul"`）和 `SoulVesselData`（`kind = "vessel"`）；以后加入其他物品类型时在 `SaveCodec` 补 kind 分支。
- 容器名（`inventory_0..inventory_9`、`vessel_cell_0..2`、`shop_0`）变化视为不兼容：旧存档里找不到的容器会 warning 并转入 `orphaned`；下一轮读档会尝试放回原容器或仓库。旧的 `cell_0..3` 就是这样迁移的。常量集中在 `Scripts/container_ids.gd`，场景里的 `container_name` 必须与之一致。`--script`/工具模式会在读档前直接返回，不会触发这个跳过逻辑。
- 仓库 10 页各自是独立容器；空页不写入 `containers`，旧存档里的 `inventory_0` 自然成为第 1 页，其余页为空。
- 读档只保证在非战斗、非拖拽状态安全；自动读档在启动时，手动读档不要在战斗中调用。
- 战斗状态不持久化：关掉游戏再开，从一场新的空战斗开始。
- 窗口位置、音量等全局设置还没有接入；以后放独立的 `user://settings.cfg`，不随新游戏重置。
- 离线收益还没有实现；`saved_at_unix` 已经写进存档，后续做挂机结算只依赖这个时间戳，不存战斗快照。

## 9. 测试

`TestAPI` 已暴露：`save_now()`、`load_save()`、`delete_save()`、`has_save()`、`get_save_path()`、`get_save_status()`、`dump_save()`。最小回归：

1. 在 `inventory_0` 放魂灵；`TestAPI.add_vessel()` + `equip_vessel()` + `vessel_add_soul()` 把魂器装进魂器槽并放魂灵；
2. `save_now()` → 清空容器 → `load_save()`；
3. 断言每个物品的 ID 和左上角格完全一致，魂器内部魂灵也回到原格；
4. 再存一次生成 `.bak`，把主文件写坏，`load_save()` 应从备份恢复；
5. 断开一个魂灵 ID 再读，确认只跳过坏条目、其余正常；魂器内部缺魂灵时只保留该条记录。

## 10. 常见排查

按「症状 → 先看 → 常见原因」顺序查，先确认不是数据/容器问题，再怀疑代码。

1. **读档后物品少了/位置变了**
   - 先看日志里的 `orphaned` 与容器 warning：ID 不在 `CollectionDB`、容器名对不上、格子被占都会走到这里；
   - 核对场景 `container_name` 与 `Scripts/container_ids.gd` 是否一致；
   - 读档前容器必须已注册（启动自动读档等一帧），手动读档不要在战斗/拖拽中调用。
2. **进度回退到旧存档**
   - 主文件解析失败时会读 `.bak`；先看 `user://saves/` 下 `slot_0.json` 与 `slot_0.json.bak` 的时间戳；
   - 从备份恢复后的第一次写盘会保留好备份（`_keep_backup_next_save`），排查时不要手动删 `.bak`。
3. **主文件和备份都读不出**
   - JSON 整体损坏或存档版本高于当前游戏时不会覆盖原文件；用 `TestAPI.get_save_path()` / `dump_save()` 定位，必要时 `delete_save()` 后重开；
   - `--script`/工具模式没有主场景，`SaveManager` 不读也不写，别在工具模式里判断存档坏了。
4. **新增物品类型读不回来**
   - `SaveCodec` 目前只编码 `kind = "soul"`；新类型要补 kind 分支和反序列化，没有该段按空处理。
5. **日志提示“容器未注册”/自动写档被禁用**
   - 启动后看 `TestAPI.get_save_status()` 的 `missing_containers`；正常主场景应为空数组；
   - 常见原因是主场景不是 `Main/control.tscn`、装备窗口未实例化，或场景 `container_name` 被改名；
   - 此时 `read_only=true`，不读档也不写档；补齐容器后重启。
