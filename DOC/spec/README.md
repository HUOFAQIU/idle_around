# 变更契约（spec）

> 类型：规范 | 状态：有效 | 核对：2026-11-23
> 何时读：准备改接口、动场景结构、新增领域行为，或要查某个决策当时为什么这么定
> 关键词：spec、契约、方案、先方案后动手、ADR、验收、退出、草稿、已约定、已实现
> 代码：`tools/scenarios/`、`tools/check.sh`
> 相关：`DOC/INDEX.md`、`指南/代码检查.md`

## 是什么

`DOC/` 其余文档写「系统应该是什么样」（设计）和「现在是什么样」（实现），长期有效。
spec 写「这一次改动把它变成什么样」：问题、方案、行为清单、测试决策、验收命令。改完就退出。

`.claude/rules/workflow.md` 的「方案先行」如果没有落盘，方案只活在对话里，换一个会话就没了。spec 是它的持久形态。

## 何时必须写

| 触发 | 例子 |
|---|---|
| 改公开接口 | `TestAPI` 方法增删改、autoload 暴露的方法、跨模块信号 |
| 动场景结构 | `.tscn` 节点层级、挂载关系、单例归属变化 |
| 新增领域行为 | 存档、战斗、地图、开局流程里玩家可见的新规则 |
| 跨 3 个以上模块的重构 | 目录重组、命名收敛、入口合并 |

临时探针、单行修复、纯文档改动不写。判断不清时按「写」处理。

## 先拷问再写

需求里有多个未定决策时，先按 `.claude/skills/grill/` 走一轮：一轮问完整条 frontier、每题附推荐答案，事实自己查、决策等用户。无论这次是否要写 spec 都适用；问空后再写草稿（若触发）或直接出方案，敲定的决策写进「实施决策」。

## 状态

- `草稿`：边讨论边记，可以反复改。
- `已约定`：用户确认了方案，可以动手。动手前必须停在这里。
- `已实现`：验收命令跑绿、代码已落地，准备「退出」。

## 每份 spec 的形状

文件：`DOC/spec/NNNN-<slug>.md`，全篇不超过 60 行。开头一段引用块：

```text
> 状态：草稿 | 日期：YYYY-MM-DD | 验收：`bash tools/check.sh --scenario <名>`
```

正文七节，缺一不可：

- `问题`：现在哪里不对，或缺什么。
- `方案`：接口、数据形状、边界；不写文件路径和代码片段，它们会腐。
- `用户可见行为`：一条一行，完整覆盖这次改动，不写「等」。
- `实施决策`：选了 A 不选 B 的理由。
- `测试决策`：在哪个 seam 上验收、为什么是它；优先最高、最少的那一个。
- `不在范围内`：明确不做的部分。
- `退出`：实现后这些内容去哪——抄进 `架构/` 或 `指南/`、转成 ADR，或直接删除。没有退出的 spec 会沉积。

## 验收

必须是本仓库能跑、且能变红的命令：

```bash
bash tools/check.sh --scenario save_roundtrip
```

「手动点一遍」不算验收；新增领域行为时，验收应落到 `指南/代码检查.md`「情景测试」里的用例。
spec 决定测什么，用例负责让它能红。

## 维护

- 活跃 spec 按编号在 `DOC/spec/` 平铺；状态改「已实现」后先 review，review 通过再执行「退出」，最后删除。
- 只有 `spec/README.md` 进 `DOC/INDEX.md` 的文档清单；单份 spec 不进，避免索引膨胀。
- 决策如果长期有效（比如「为什么用场景而不是 `--script`」），退出时写成 `adr/NNNN-<slug>.md` 并在 `adr/README.md` 登记，不要留在 spec 里。
