# 工作流加固

> 状态：已约定 | 日期：2026-11-21 | 验收：`bash tools/check.sh --all`

## 问题

避雷针演练暴露了流程与文档层的结构性问题：review 在 spec 删除后才跑，交接单在 commit 前写；`DOC/INDEX.md` 的核对日期靠人工同步，已经漂移；触发器事件清单散落在 8 篇文档里，改一处要扇出；`CLAUDE.md` 大量否定句，执行时还要反推默认动作；缺统一术语和长期决策的落点；`project.godot` 常驻无内容 diff 的 `M`。

## 方案

1. 流程顺序：review 固定在 spec「已实现」之后、「退出」之前；handoff 默认在 commit 之后，未提交时明确标注。
2. INDEX 元数据：新增校验工具，比对文档头与清单行的类型、状态、核对日期，纳入全量检查；配一次性修复入口。
3. 触发器文档：以「战斗数据与魂灵」的触发器节为唯一权威，其余文档改为指针，只保留本地流程或排查示例。
4. `CLAUDE.md`：把禁止句改成「默认做 X；只有 Y 时才 Z」，硬约束保留为必须。
5. 术语表：一词一行，只给唯一权威指针，不复制规则正文。
6. ADR：新建 `DOC/adr/`，记录长期决策；接受后不改历史，用新 ADR 取代。
7. 仓库卫生：用定点 `.gitattributes` 和 `git add --renormalize` 修 `project.godot` 的幻影改动，不扩大到全仓库换行重写。

## 用户可见行为

- 维护者按 review skill 执行时，spec 仍在且状态为「已实现」；spec 已删时能从 git 历史读取。
- 交接单默认写「已提交」并附 commit；未提交时明确写「待提交」和提交命令。
- 改文档内容后忘记同步 INDEX 日期，全量检查会红。
- 查触发器事件只需要读「战斗数据与魂灵」一处；其余文档给指针。
- `CLAUDE.md` 每条规则都能直接执行，不需要反推「那到底该做什么」。
- 查术语从 `DOC/术语表.md` 进入；查历史决策从 `DOC/adr/` 进入。
- `git status` 不再常驻 `project.godot` 的幻影改动。

## 实施决策

- INDEX 用校验而不是纯人工规则：人工规则已经漂移过一次，校验能让它变红；保留清单顺序，不做全表重排。
- 术语表只写一行定义 + 指针，避免与正文形成第二份会腐的规范。
- ADR 只收长期有效的决策；一次性实现细节留在 spec 或架构文档。
- 触发器权威表放在「战斗数据与魂灵」，因为事件、payload、派发和 `max_range` 都在那里。
- `project.godot` 先诊断再修；优先定点属性，不做仓库级 `text=auto` 重写。

## 测试决策

- 全量验收命令：`bash tools/check.sh --all`。
- INDEX 校验要有红测：故意改错一条日期，检查必须失败；修回后恢复绿。
- 流程顺序与文档去重不写自动测试，靠 skill 文本和 grep 核对；这是文档一致性，不是领域行为。

## 不在范围内

- 不改游戏行为、内容数值、TestAPI 入口。
- 不重写现有架构文档的正文，只做去重和指针化。
- 不引入文档生成器；INDEX 清单仍是手写文件，只加校验。
- 不处理 `project.godot` 之外的换行问题。

## 退出

流程规则并入 `指南/Claude Code 项目结构.md`、`指南/代码检查.md` 和 `spec/README.md`；长期决策转 ADR；完成后删除本 spec。
