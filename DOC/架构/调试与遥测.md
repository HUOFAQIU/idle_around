## 1. 设计目标

战斗是自动化的，靠看画面很难判断“这颗魂灵为什么没放、触发器为什么没触发、状态是谁施加的”。遥测层解决三件事：

1. **事件化**：施法、选目标、效果施加、状态、周期 tick、触发器、充能、死亡、掉落都变成带时间戳的事件；
2. **可追溯**：一次施法派生出的效果/触发/充能共享一条 `trace`，能还原因果链；
3. **不侵入**：事件记录不参与战斗判定；关掉 `CombatTelemetry.enabled` 后 `record()` 立即返回。

## 2. 组成

```
BattleManager / BattleUnit / AutoCastAbility / SoulTriggerAbility / BattleBrain
        │  emit_event(category, type, fields, importance)
        ▼
BattleEventBus（每场一个，BattleManager.events）
        ├─ emitted ─────────────► CombatTelemetryAdapter ─► CombatTelemetry
        ├─ emitted ─────────────► BattleLogAdapter ───────► InfoWindow.append_line ─► TerminalView
        ├─ emitted ─────────────► CombatConsoleAdapter ───► print_rich
        ├─ unit_asc_ready ──────► CombatTelemetryAdapter ─► bind_unit()
        ├─ soul_runtime_created ► CombatTelemetryAdapter ─► bind_ability()
        └─ 信号 + emitted ──────► CombatNarrator ─────────► log/line（回到总线）

CombatTelemetry (Autoload)
        ├─ 环形事件缓冲 events
        ├─ event_recorded 信号 ──────────────► DebugWindow 时间线
        ├─ 可选 JSONL 文件 (user://debug)
        └─ query / get_trace_chain / export_jsonl

SoulLoadout（BattleUnit.add_soul_abilities() 委托）
        │ 逐颗魂灵建 SoulRuntime
        ▼
SoulRuntimeDB (Autoload)
        ├─ 玩家已装备 SoulData 实例 → SoulRuntime
        ├─ runtime_registered / runtime_unregistered ─► ItemView 绑定/解绑
        └─ player_runtimes() / all() ─────────────────► DebugWindow 总览/魂灵页
           （怪物魂灵不注册：可能多只怪共享同一份 SoulData；快照读 BattleUnit.loadout）
```

关键原则：

- 模拟层只发 `BattleEvent`，不直接引用 `CombatTelemetry` / `InfoWindow` / `print_rich`；观察者由 `BattleWindow` 开战时挂到 `BattleEventBus` 上，随这一场销毁。
- 总线事件可以带 `BattleUnit` / `GameplayEffectSpec` / `CombatTrace` 等运行时引用；`CombatTelemetry` 入缓冲前由 `CombatTelemetrySchema.unit_info()` 转成 `{id, name, team}`，**缓冲里不存 Node**。
- `SoulData` 只放静态数据；扫描线、加速/减速/冻结、统计都在 `SoulRuntime`。
- 升级 `addons/GodotGAS` 时保留项目侧已有修改（`periodic_effect_ticked`、`EditorInterface` 单例化等，见 `架构/GAS.md`）；项目侧通过 `SoulEffectContext`（`GameplayEffectContext` 子类）携带 trace。

## 3. 事件模型

模拟层用 `BattleEvent`（`category / type / fields / importance`）发事件，适配器原样转给 `CombatTelemetry.record()`；入缓冲后补齐统一字段：

| 字段 | 说明 |
|---|---|
| `seq` | 全局自增序号 |
| `run_id` | 战斗场次；`BattleSession.run_id` |
| `frame` | 进程帧 |
| `t` | 战斗内秒数 |
| `category` | `battle / cast / soul / trigger / effect / attribute / tag / cue / log / system` |
| `type` | 事件类型，调试窗口负责翻译成中文 |
| `importance` | `important`（全局记录）或 `detail`（只记录关注单位） |
| `actor` / `target` / `unit` | `{id, name, team}`，由 `actor_unit` 等转换 |
| `soul` / `ability` / `ability_tag` / `effect` | 魂灵/技能/效果标识 |
| `amount` / `health_delta` / `shield_delta` / `burn_delta` | 数值 |
| `trace_id` / `parent_trace_id` / `root_trace_id` | 因果链 |
| `detail` | 人类可读补充 |
| `color` | 时间线颜色 |

重要度规则：

- 玩家相关（玩家施法、玩家受击、玩家状态、玩家死亡）→ `important`；
- 敌人细节（敌人属性变化、周期 tick、移动、充能）→ `detail`；
- `detail` 只有 `watch_unit_id` 指向的单位或 `record_detail_globally = true` 才入缓冲，避免无限刷怪冲爆缓冲。

## 4. 因果链

`CombatTrace` 只保存 id / parent_id / root_id / cause：

```
cast:<魂灵名> (trace 1)
├─ soul used
├─ effect 伤害 (trace 1)
└─ BattleUnit 日志/飘字
```

`AutoCastAbility` 从 `try_activate()` 的 payload 读取父 trace；每次施法创建 `cast:<技能名>`。效果 spec 用 `SoulEffectContext` 携带 trace；触发器、充能、周期 tick 继承父 trace。`CombatTelemetry.get_trace_chain(trace_id)` 返回同一 root 下的事件。

- trace id 全局自增，不按战斗重置，避免旧事件和新事件撞号。
- 项目侧创建的 spec 必须用 `SoulEffectContext` 携带 trace；GAS 内部便捷路径创建的 context 没有 trace，调试按「无 trace」处理。
- 周期效果施加时的 `calculated_deltas` 只是预览，真实伤害在每跳 tick；施加事件由 `active_effect_added` 记录，不要伪造一次伤害事件。

## 5. 接入点

| 文件 | 发出的事件 |
|---|---|
| `BattleManager` | `battle/unit_added`、`battle/moved`、`battle/enemy_in_range`、`battle/enemy_out_of_range`、`battle/drop_roll`、`battle/drop`、`log/line` |
| `BattleUnit` | 绑定信号 `unit_asc_ready`（技能授予前）、`soul_runtime_created`（每颗主动魂灵） |
| `AutoCastAbility` | `cast/attempt`、`activate`、`release`、`cast_start`、`empty`、`targets`、`crit`、`projectiles` 等，以及 `soul/used` |
| `SoulTriggerAbility` | `trigger/fired` |
| `BattleBrain` | `soul/pending`、`soul/flush_skip` |
| `ChargedAbility` | 不直接发事件；`became_ready` / `charge_added` / `status_applied` / `status_expired` 由适配器绑定后转成 `soul/*` |
| `CombatNarrator` | 不直接发业务事件；订阅 ASC/技能信号与 `cast/*`、`trigger/fired`、`battle/drop`，生成中文 `log/line` |
| GAS ASC 信号 | 由适配器绑定：属性变化、标签增删/层数、ActiveEffect 增删、周期 tick、能力授予/失败、GameplayEvent |
| `BattleWindow` | 创建/丢弃遥测/日志/控制台/叙事四个观察者；`CombatTelemetry.begin_run` / `end_run`、loadout 快照、关注玩家 |

- `bind_ability()` 必须在 `SoulRuntime` 建好后调用，主动魂灵信号要挂到对应 runtime。
- 事件观察者要在生成单位前挂载，否则会漏掉 `unit_asc_ready` 和首批战斗事件。
- 空放播报策略：含魂灵步骤的技能总是播报，纯单位技能只播报我方。

## 6. 性能约定

- 不记录每物理帧充能；只记录外部充能、状态、激活、触发。
- 移动只在跨格时记录，且是 `detail`。
- 敌人默认只记录重要事件；玩家和关注单位才记录详细事件。`record()` 对 `detail` 事件先在 `duplicate` / 归一化之前判断有无关注对象，没有就直接丢弃。
- 战斗快照同理：敌人只给摘要，玩家和选中单位才展开完整属性/效果，避免无限刷怪时每帧展开全部。
- ASC 信号只对玩家和当前关注单位全量绑定；其他敌人只绑 `died`（重要事件），`watch_unit()` 关注时再补绑详细信号。
- 充能统计由 `ChargedAbility.add_charge()` 的 `_on_charge_received()` 钩子写入 `SoulRuntime`，遥测只负责事件，不再修改玩法计数。
- 环形缓冲默认 5000 条；`max_events` 可调。溢出时一次裁掉约 10%，不逐条搬数组；不报错，只按实际裁剪数累计 `dropped_events`。
- JSONL 录制每 `FILE_FLUSH_EVERY`（50）行 flush 一次，关闭文件/结束场次时统一 flush。
- DebugWindow 只在自己可见时轮询；快照只在总览/单位/触发器/GAS 页构建，树列表 2Hz 且只刷新当前页签；搜索框 200ms 防抖；关闭时不轮询。关闭「跟随」后时间线和日志停在当前位置；暂停期间日志不追加，恢复时从缓冲补齐；点选历史事件会主动停止跟随；魂灵贡献归属优先看 `event.soul`，否则用 `trace_cause` 里的来源名匹配。
- 字符串/JSON 格式化只在 UI 或导出时做，记录路径只存原始字段。

## 7. 新增一个调试事件

1. 在 `game/battle/battle_event.gd` 选定 `category`（没有合适的再加 `CATEGORY_*`）；`Scripts/debug/combat_telemetry_schema.gd` 的分类常量直接引用它，调试窗口无需另改；
2. 在模拟层触发点发总线事件：
   ```gdscript
   battle.events.emit_event(BattleEvent.CATEGORY_CAST, "your_event", {
       "actor_unit": caster,
       "target_unit": target,
       "soul": soul_name,
       "effect": effect_name,
       "amount": value,
       "trace": trace,
       "detail": "人类可读说明",
   }, BattleEvent.IMPORTANCE_DETAIL)
   ```
   `CombatTelemetryAdapter` 会自动转成 `CombatTelemetry.record()`；不要绕过总线直接调遥测。
3. 需要详细事件时用 `BattleEvent.IMPORTANCE_DETAIL`，并确保关注单位能覆盖；
4. 需要进战斗信息窗时，用 `CATEGORY_LOG` + `{"text", "color"}`；`BattleLogAdapter` 会转给 `InfoWindow.append_line()`，再写进 `TerminalView`。中文文案集中在 `game/battle/combat_narrator.gd`，新增叙事事件时优先扩展它，不要回到模拟层拼字符串；
5. 在 `Windows/Debug/debug_window.gd` 的 `TYPE_NAMES` 加中文名（没有会显示英文 type）；
6. 更新本文件的接入点表格。

不要在这里写战斗判定；需要“为什么没放”时，记录原因字符串即可。

## 9. 现状与后续

- 模拟层已通过 `BattleEventBus` 发事件，遥测/战斗信息窗/控制台都是订阅者；中文战斗叙事由 `CombatNarrator` 订阅事件生成，`BattleUnit` / 技能步骤只发事件。
- 触发器已迁移到 `SoulTriggerAbility` + GAS GameplayEvent；`PassiveTrigger.event_tag` 走标签，调试窗口的 `TRIGGER` 事件和 `GAS` 页会看到 `Event.*`。
- 目前 `Cue` 的实际播放没有信号可监听（addon 的 `GameplayCueManager` 没有暴露信号），调试窗口只显示效果挂了哪些 Cue 标签和注册表内容。
- `SoulRuntime.counters` 暂以字符串键字典保存；后续若统计项稳定，可以改成强类型字段。

## 10. 启动耗时打点

`Scripts/debug/startup_timing.gd`（`StartupTiming`）在开发期把启动各阶段耗时打到控制台，编辑器里直接显示在 Output 面板：

```text
[启动] 首个 autoload：+1705 ms（累计 1705 ms）
[启动] mod 加载完成：+161 ms（累计 1866 ms）
[启动] GBIS 等前置 autoload 完成：+2141 ms（累计 4007 ms）
[启动] autoload 全部就绪：+11 ms（累计 4018 ms）
[启动] 主场景就绪：+189 ms（累计 4207 ms）
[启动] 首帧绘制：+161 ms（累计 4368 ms）
```

- 时间基准是 `Time.get_ticks_msec()`，0 点是引擎启动，不含进程创建到引擎初始化的时间；
- 打点位置：`ModLoader._init`、`CollectionDB._ready`、`GameFlow._ready`、主场景 `_ready` + 首帧 `frame_post_draw`；
- 常驻开启、无开关；调用点用 `preload` 引用，避免 `--script` 模式找不到全局类名。后续嫌吵可加命令行参数控制。
