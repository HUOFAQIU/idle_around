## 1. 战斗数据 `base_mods/core/`

### 1.1 `SkillDefinition` 与步骤

`SkillDefinition`（`game/content/skill_definition.gd`）= 共享配置 + 有序的 `steps` 数组；字段以脚本的 `@export` 为准，步骤字段分别在 `UnitSkillStep` / `SoulSkillStep`。每一步自己决定目标域、选目标规则和结算方式；一个技能可以同时有单位步骤、魂灵步骤，或两者混合。

执行约定：

- `AutoCastAbility._release_once()` 创建 `SkillCastContext`，按 `steps` 顺序交给 `_run_step()` 按类型分派（`SkillStep` 只作类型标记，执行在 `game/battle/`）；
- 每步返回 `SkillStepResult(hit, empty_reason)`；只要有一个 step 命中，本次释放就算命中；
- 全部步骤都空放才记一次空放；
- `SkillCastContext.blackboard` 用于步骤间传数据（例如前一步选中的目标）；运行时状态不能写进共享的 `SkillStep` 资源；
- 投射物落地回调绑定发起它的 step，每支箭结算自己的 effects/cue。
- 场景节点直接配 skill 时入树才 apply；代码创建的技能在 grant 前已 apply、`ability_name` 非空，避免重复执行。
- 空放播报策略：含魂灵步骤的技能总是播报，纯单位技能只播报我方。

技能显示名不在这份数据里：`AutoCastAbility.ability_name` 来自魂灵的 `ItemData.item_name`，没传时退回 `SkillDefinition.id`。

`ModLoader` 校验每个 step：`UnitSkillStep` 的 `target_rule` 必须是 `TargetRule` 且至少有 `effects` 或 `projectile_scene`；`SoulSkillStep` 的 `target_rule` 必须是 `SoulTargetRule` 且至少有一个状态时长；`steps` 为空且 `self_effects` 为空会报错。

所有 `*_duration` 和 `cooldown_seconds` 在资源里仍然是秒；内部刻度换算见 `架构/战斗运行时_施法与冷却.md` §1.4。

`cast_times > 1` 的多重触发语义见 `设计/魂灵.md`；每次释放按 `steps` 重新选目标、先结算 `self_effects` 再执行 steps。

`UnitSkillStep` 配了 `hit_cue_tag` 时，每次结算到目标身上都会在目标身上播一次命中特效；方向按这个 step 自己的命中次数交替（第 1 次右→左，第 2 次左→右），打空不消耗次数。这一击打死目标时改挂到战场单位层、按目标最后的位置播放，避免 Cue 跟着当场销毁的单位一起没。

### 1.2 `TargetRule`（`target_rule.gd`）

`TargetRule` 和 `SoulTargetRule` 都继承 `TargetRuleBase`；消费端按 `TargetRuleBase.domain()` 分派，不再按具体类型判断。两个子类各自实现：

- `domain()`：`TargetRule` 返回 `Domain.UNIT`，`SoulTargetRule` 返回 `Domain.SOUL`；基类未实现时 `push_error` 并返回 `UNIT`，避免静默走错分支。
- `max_range_cells()`：工具提示用的格数；`TargetRule` 返回 `max_range`，魂灵规则默认 0。

`ModLoader` 在加载时校验规则类型与技能字段一致：单位目标技能不能配魂灵状态时长；魂灵目标技能不能配 `effects` / `projectile_scene` / `hit_cue_tag`，且至少要有一个状态时长。自定义 `TargetRuleBase` 子类目前必须落在 `TargetRule` / `SoulTargetRule` 体系内，否则加载时报错。

字段与 `Mode` / `Camp` 枚举见 `game/battle/target_rule.gd`，语义要点：

`resolve()` 返回“批次数组” `Array[Array[BattleUnit]]`：

- `RANDOM / LOWEST_HP_PERCENT / ALL / NEAREST` → 只产生 1 个批次（一次打多个目标）；
- `REPEAT` → 产生 `count` 个批次，每批 1 个目标，保证每次独立结算。框架 `get_target_nodes()` 会去重，不拆批次就拿不到独立暴击/飘字/日志。
- 死亡单位可能仍在名册/索引中，目标筛选用 `is_dead` 字段，而不是只看 `State.Dead` 标签。
- `NEAREST` 只取 1 个时用单次扫描，避免为一次选目标排序整个候选名单。

### 1.3 `SoulTargetRule`（`soul_target_rule.gd`）

给“以魂灵为目标”的技能用；和 `TargetRule` 一样继承 `TargetRuleBase`（`domain()` 返回 `SOUL`），但选的是魂灵能力，返回类型也不同。

字段与 `Mode` 枚举见 `game/battle/soul_target_rule.gd`，语义要点：

`resolve(caster, rng)` 返回 `Array[ChargedAbility]`；选中魂灵后由 `SoulSkillStep` 的 `haste_duration` / `slow_duration` / `freeze_duration` / `charge_duration` 决定施加什么：

- 候选只来自 `caster.unit_soul_abilities`，且 `cooldown > 0`；
- 玩家和怪物都适用：玩家魂灵栏来自角色魂器网格里的战斗魂器，怪物魂灵栏由 `MonsterData.soul_entries` 生成；
- 无冷却魂灵当前没有设计，先直接排除，等以后补规则；
- `LEFT / RIGHT / BOTH_SIDES` 只比较同一 `soul_container`，不跨魂器；不同魂器的魂灵互不相邻；
- `BOTH_SIDES` 同时检查左右两侧；空位、无冷却魂灵跳过，两边都没有才空放；
- 相邻判定用 `SoulSlot` 的 `column / width`：
  - 右侧：目标最左列 = 施法者最左列 + 施法者列宽；
  - 左侧：目标最左列 + 目标列宽 = 施法者最左列；
- 相邻判定统一走 `SoulTargetRule.is_adjacent(a, b)`，`PassiveTrigger` 的“使用相邻魂灵”筛选复用它；
- 相邻判定只比较列区间、不比较行，前提是魂灵与魂器均为 2 行；多行魂器需要把行信息补进 `SoulSlot`。
- 没有目标就返回空数组，技能空放并照常消耗冷却。

### 1.4 怪物魂灵与掉落（`MonsterSoulEntry` / `DropEntry`）

`MonsterSoulEntry`（`game/content/monster_soul_entry.gd`）是怪物携带魂灵的唯一配置源：

| 字段 | 说明 |
|---|---|
| `soul: SoulData` | 携带的魂灵；怪物没有魂器，按列表顺序生成虚拟魂灵栏 |
| `drop_chance: float` | 0~1，默认 0.2；每颗魂灵独立配置 |

`MonsterData.soul_entries` 同时决定两件事：

- `soul_list()`：按配置顺序取出魂灵，交给 `SoulLoadout` 生成技能和虚拟魂灵栏；
- `drop_entries()`：把每颗魂灵转成运行时 `DropEntry`（`item = soul`，`chance = drop_chance`）。

`DropEntry`（`game/content/drops/drop_entry.gd`）只负责运行时掷骰：

| 字段 | 说明 |
|---|---|
| `item: ItemData` | 掉什么；魂灵就是 `SoulData` |
| `chance: float` | 0~1，默认 0.2；每条独立掷骰 |

怪死亡时 `LootRoller.roll()` 对每条掉落各判定一次，成功就调用注入的 `Warehouse.add_item(item)`（从仓库第 1 页开始找空位），10 页全满才写日志丢失。因为掉落由携带魂灵自动生成，“怪物能掉落它所有的魂灵”不需要再手配一份掉落表。

### 1.5 魂灵与技能实现经验

路径：`base_mods/core/souls/<名字>/`

- 主动魂灵：`SoulData.skill` 指向 `SkillDefinition`，由 `SoulLoadout` 生成 `AutoCastAbility`；显示名取 `item_name`。冷却读 `SkillDefinition.cooldown_seconds`，实例带冷却情绪时由 `AutoCastAbility.apply_soul_emotions()` 覆盖。投射物速度由 `UnitSkillStep.projectile_speed` 控制，默认 420；`effect_duration` / `PassiveTrigger.effect_duration` > 0 时覆盖本次施加的时长。
- 被动魂灵：使用 `PassiveSoulData`，没有冷却、不进入自动施法队列、不显示扫描线；`passive_effects` 在血条绑定和 `_connect_asc()` 之前挂到玩家 ASC，因此不会产生开场状态日志。属性效果用 `PassiveEffect` 类型标记，`BattleUnit` 按类型决定是否写日志。被动魂灵占格，会阻断左右相邻。
- 类型与标签：`SoulData.types` / `SoulData.tags` 的语义、尺寸与命名见 `设计/魂灵.md`；两者与 GAS 的 `GameplayTags` 是两套东西。
- 魂灵触发器：`SoulData.triggers` 配 `PassiveTrigger`，主动/被动魂灵通用。`SoulLoadout` 为每条触发器生成一个 `SoulTriggerAbility`（`GameplayAbility` 子类），grant 到 ASC 并把 `PassiveTrigger.event_tag` 写进 `trigger_event_tag`。它**不进入** `BattleBrain.abilities`，不会被主循环自动施放，只由 `ASC.send_gameplay_event()` 按标签唤醒；payload 至少带 `target` 和 `trace`。以下事件清单是唯一权威，其它文档只引用本节。
  - `Event.Movement.UnitMoved`：`BattleUnit.on_enemy_moved()` 只对敌方移动发送；只有带该触发器的单位会注册到 `BattleManager`，移动事件只派发给注册者。
  - `Event.Health.BelowPercent`：`attribute_changed` 里生命下降时发送，payload 带旧值/新值/比例；`SoulTriggerAbility` 按 `threshold_ratio` 严格小于判断，`once_per_battle` 控制只触发一次。
  - `Event.Combat.SoulUsed`：另一个魂灵技能成功激活（含空放）时由 `AutoCastAbility._notify_soul_used()` 发送；`SoulTriggerAbility` 排除来源自己，`required_soul_types` 要求被使用魂灵带齐类型，`require_adjacent` 要求同一魂器容器内紧邻。命中后按 `charge_source_seconds` 给来源魂灵充能；充满时由 `BattleBrain.request_activation()` 入队、当帧末统一释放，受 20 刻激活锁限制（同一颗魂灵 1 秒最多 6 次）。当前没有魂灵配置该事件。
  - `Event.Combat.FreezeApplied`：任何单位被冻结时，向所有以它为敌、且确实带该触发器事件的单位发送（`BattleManager` 维护监听者注册表，只遍历这些单位，不扫全场）；每冻住一个目标触发一次，重复冻结同一目标也算，不区分冻结来源。配置后可用 `charge_source_seconds` 在冻结时给来源魂灵充能；`base_mods/core/souls/bi_lei_zhen/` 的避雷针用它造成触发伤害。
  - `Event.Combat.SlowApplied`：魂灵级减速（`ChargedAbility.apply_slow()`）施加时，由被减速魂灵所属单位调用 `BattleUnit.notify_slow_applied()`，向敌对且确实带该触发器事件的单位发送；payload 的 `target` / `source` 都是被减速单位。单位级 `State.Sluggish` 已实现，但走 `sluggish_unit.tres` 施加时不发这个事件，所以仍只有魂灵级减速会触发。
  - `target_scope` 支持事件目标 / 自己 / 全体敌人；`max_range`（格，0 = 不限）按持有者与目标的距离过滤 `EVENT_TARGET` 与 `ALL_ENEMIES`，超出射程不施加效果；触发效果通过 spec 的 SetByCaller `Data.TriggerMagnitude` 传数值，不在效果资源里写死。
  - `charge_source_seconds` 在触发后给来源主动魂灵充能；被动魂灵没有来源技能，忽略该字段。
  - `trigger_name` 非空时写一行“触发【名字】”日志；留空保持原有静默行为。
  - 只有 ASC 上确实存在对应 `trigger_event_tag` 的触发器时才发送事件，避免无监听者的事件刷屏。
- 执行器映射：直接伤害挂 `SoulDamageExecution`，伤害+剧毒挂 `PoisonDamageExecution`，护盾获得挂 `ShieldExecution`，单独施加灼烧/剧毒/生命再生挂 `StatusApplyExecution`，治疗挂 `HealExecution`；治疗、灼烧、剧毒、生命再生周期本身不要挂直接伤害。伤害加成、暴击与取整口径见 `架构/战斗运行时_伤害与流程.md` §1.1；暴击倍率读取与标签注入统一走 `game/battle/crit_resolution.gd`，execution 不各自复制。
- 持续伤害/生命再生：周期效果继承 `PeriodicStatusTickExecution`（灼烧 `BurnTickExecution`，剧毒/生命再生复用 `NetStatusTickExecution`）；新增周期状态只需继承基类并补 `status_attribute` / `status_display_name` / `remove_when_zero` / `log_color` / `popup_style` / `is_heal`，不改 `BattleUnit` / `UnitPresenter` / `CombatNarrator` / `CombatNames`。
- 扫描线 / 徽章 / 颜色：只有主动魂灵显示扫描线，资源里的 `soul_scanline.gdshader` 按需打开；加速/减速剩余秒数显示在魂器网格的魂灵实例上，充能瞬时、不显示徽章；tooltip / 日志 / 飘字 / 状态条统一读 `GameColors`，显示名到颜色的映射在 `STATUS`。
- 魂器：`content.vessels` 注册 `SoulVesselData`；`BattleWindow._equipped_souls()` 读取内部魂灵生成 `SoulSlot`，效果由 `SoulVesselEffect` 描述、`SoulRuntime.vessel_damage_bonus` 汇总。详细规则见 `设计/魂器.md`。
- tooltip：正文、占位符与动态伤害预览的规则见 `设计/魂灵.md`；技能和触发器资源不带展示文案。
- 调试入口：新魂灵用 `TestAPI.add_soul()`（不传容器即自动找空页）放进仓库，`TestAPI.set_warehouse_page()` 可切页查看；正式入口由掉落/商店决定。

### 1.6 冷却与持续效果资源

- 技能冷却不再有 `GameplayEffect` 资源：`SkillDefinition.cooldown_seconds` 是唯一时长来源，`ChargedAbility` 按充能模型管理；`GameplayAbility.cooldown_effect` 保持为空。
- 怪物移动已改为即时制；名字、血量、攻击范围、移速、刷新距离、贴图都配在 `MonsterData`，由 `BattleSession._spawn_enemy()` 注入 `BattleUnit`，场景只保留碰撞体/节点结构。
- 刷新距离：`MonsterData.spawn_distances`（`Array[int]`，单位格，默认 `[3]`）决定这只怪可以刷在离角色几格；刷怪时把这些距离环的格子合并后随机选一格。选怪在选格之前，`BattleSession` 先选怪再按它的距离选格；请求的距离都没有格子时退到最近的有格环。`ModLoader` 校验数组非空且每个距离 `>= 1`。

持续效果资源：

- 施加：`burn_apply.tres` / `poison_apply.tres` / `regen_apply.tres` 都是 `INSTANT` + `StatusApplyExecution`，分别写 `burn` / `poison` / `regen`；数值优先级是 `Data.SkillMagnitude` > `Data.TriggerMagnitude` > 效果资源 `base_amount`，之后再乘暴击倍率。
- 周期：`burn_tick.tres`（0.5 秒、衰减、对护盾减半）、`poison_tick.tres` / `regen_tick.tres`（1 秒、按净值）；三者都是 `INFINITE`、`max_stacks = 1`，分别挂对应 execution。
- 单位状态：`freeze_unit.tres`（`DURATION` 1 秒、`REFRESH_DURATION`、`State.Frozen` + 冻结 Cue）；`swift_unit.tres` / `sluggish_unit.tres` 对 `move_speed` 做 `PERCENT_ADD ±0.5`。
- 触发伤害：`trigger_damage_50.tres` 挂 `SoulDamageExecution(base_damage = 50)`，吃触发者的 `damage_bonus` 与暴击规则，不读 `Data.TriggerMagnitude`。
- 这些资源不填 `resource_name`；日志名由 `CombatNames` / `CombatNarrator` 统一。

### 1.7 怪物数据与见闻清单

见闻窗口的“全部条目”来自 `base_mods/core/mod.json` 和第三方 mod 的 manifest；`Scripts/collection_db.gd` 从 ModLoader 条目构建运行时索引与已遇见状态（存档见 `架构/存档.md`）。

- ID 由 manifest 的 `id` 字段决定（core 不带前缀，第三方带 `<mod_id>:` 前缀），同时是“已遇见”存档的键；文件改名/移动不影响 ID；
- 新增魂灵/怪物时，在 `base_mods/core/mod.json` 加条目，不再依赖编辑器扫描；怪物可用 `spawn_distances` 配置刷新距离数组；
- 解锁时机：怪物首次刷出即记录；魂灵首次进背包、魂器首次进入任意容器即记录。`GBIS.add_item()` 会调用 `ItemData.make_instance()` 复制物品，副本没有 `resource_path`，但 `content_id` 随副本保留，`CollectionDB` 直接读取；
- 未遇见条目仍占位显示，但不暴露名字和图标。

### 1.8 地图数据（`MapData` / `MapSpawnEntry`）

地图暂不进 mod manifest，硬编码在 `game/content/map_catalog.gd` 的 `MapCatalog`：

字段以 `game/content/map_data.gd` / `map_spawn_entry.gd` 为准（`TIME_INTERVAL` / `KILL_COUNT` 两种刷怪条件）；具体地图的怪物、总量、间隔配在 `base_mods/core/maps/<name>/` 的 `.tres` 里，森林图见 `forest_map.tres`。地图实例是 `game/content/map_item_data.gd`（2×2、`MAP`），数量石是 `game/content/quantity_stone_data.gd`（1×1、`STONE`，使用功能未实现）。

地图条目的怪物 id 是 `content_id`，运行时由 `CollectionDB` 解析，避免提前加载怪物资源；完整规则见 `设计/地图与战斗.md`。

### 1.9 魂灵情绪（实现）

设计规则（16 种情绪、抽签、映射、稀有度）见 `设计/情绪系统.md`；本节只记实现数据流。

- 数据：`SoulData.emotion_ranges` 是模板声明（情绪 ID → `Vector2(左端, 右端)`），`SoulData.emotions` 是实例构成（情绪 ID → 整数百分比，合计 100）。`make_instance()` 显式复制 `emotions`，模板声明留在共享资源上。
- 常量：`SoulEmotion` 维护 16 个 ID、中文名、稀有度名与总量区间、有效情绪判定（除冷却外且已声明）；读取字典时同时接受 `StringName` 与 `String` 键。
- 抽签：`SoulEmotionRoller.roll()` 在掉落成功时调用。有效情绪先占位，超过 6 种随机取 6，不足用杂情绪补满；有效总量按地图稀有度切分，剩余给杂情绪。没有 `emotion_ranges` 的魂灵不做任何事。
- 映射：`SoulEmotionValues` 提供 `share` / `value` / `damage_base` / `cooldown_seconds` / `cast_times`。魂灵未声明该参数时返回 -1（伤害/冷却）或 0（多重触发），调用方回落到技能模板；声明了但构成里没有（只有冷却会这样）时按占比 0 取范围左端。
- 接线：`LootRoller.roll(unit, rng, rarity)` 生成实例；`BattleSession` 把 `MapData.rarity` 传给 `BattleManager.loot_rarity`。伤害在 `SoulDamageExecution` 里通过 `spec.context.soul_runtime.soul` 读取实例值，不修改共享技能资源；`SoulDamagePreview` 与 tooltip 同样按实例取伤害、冷却、多重触发。
- 存档：`SaveCodec` 只在构成非空时写 `emotions`（字符串键）；读档校验 ID 并夹取百分比。副本再由 `InventoryService.add_item()` 走一次 `make_instance()`，构成因覆写而保留。
- tooltip：`SoulTooltip` 用实例 `SoulData` 构建正文数值并追加情绪段；杂情绪行带 `TooltipText.DIM_PREFIX` 前缀，渲染为次要色。
- 地图：`MapData.rarity`（1~5，默认 1）由 `ModLoader` 校验；`MapTooltip` 显示稀有度名称。
