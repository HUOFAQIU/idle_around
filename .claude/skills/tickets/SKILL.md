# 大改拆批

先判断要不要拆：一份 spec 能写完、一次 `bash tools/check.sh --all` 能验收的，不拆，直接做。

## 切分三原则

### 1. Vertical slice

每一批从真实入口打通到可见结果，而不是「先所有数据层、再所有 UI」。每批结束仓库必须是绿的、能演示。

例：加「删除存档槽位」= 存档域方法 + TestAPI 转发 + 窗口按钮 + 情景用例，一批完成；不是先写四个域、最后一起接 UI。

### 2. 先落阻塞边

所有后续批次都依赖的接口、数据结构、场景节点、manifest 字段，单独成第一批并先落地。阻塞边没定，后面批次都在猜，返工率最高。

判断方法：画批次依赖图，入度为 0 的先做。如果某批要等三批，检查阻塞边是不是被拆碎了。

### 3. Expand–contract

改共享接口时分三步：

1. expand：加新路径，旧路径继续可用；
2. 迁移调用方，逐批改到新路径；
3. contract：调用方清零后删旧路径。

不要在同一批里既加新又删旧。适用于代码接口（TestAPI、autoload、跨模块信号）；存档和设置格式不适用，开发期允许直接破坏。

## 每批交付物

- 一份 spec，触发条件见 `DOC/spec/README.md`「何时必须写」。
- 一条能变红也能变绿的验收命令；领域行为落进 `tools/scenarios/cases/`。
- 一个 commit；跨会话时按 `handoff` skill 写交接。

批次间有依赖就串行；无依赖且文件不重叠才可并行。

## 输出格式

先给表，再动手：

| # | 目标 | 依赖 | 验收命令 | 涉及模块或文件 |
|---|---|---|---|---|

「目标」写成用户可见或可测的结果，不写「重构 X」。给完等确认（`.claude/rules/workflow.md`「方案先行」），确认后按序执行。

全部批次完成后跑一次 `bash tools/check.sh --all`；跨批次的教训写进 `DOC/架构/现状与注意.md`。
