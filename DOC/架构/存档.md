## 1. 设计原则

- **六槽**：`user://saves/slot_0.json` … `slot_5.json`，界面显示为「存档 1」…「存档 6」。每个槽是独立的一份文档、独立的 `.bak` / `.tmp`。
- **启动不自动读档**：`SaveManager._ready()` 只扫描六个槽的摘要；进入游戏必须由 `GameFlow` 选择已有槽或创建新档。没有活动槽时不累计 `play_time_sec`、不心跳写盘、关窗也不写。
- **只存玩家做了什么**：容器里的物品（`content_id` + 左上角格）、魂器内部的魂灵、见闻已解锁（怪物/魂灵/魂器）、角色身份（`character_id` + `display_name`）、`saved_at_unix`、`play_time_sec`。魂灵冷却、HP、怪物、扫描线、`SoulRuntime` 等战斗运行期状态一律不存，读档后从新一场开始。
- **静态数据不进存档**：不存资源路径、不存 `ItemData` 的静态字段；读档按 ID 从 `CollectionDB` 重建。角色数值以 `CharacterDefinition.profile` 为准，旧档只保留角色 ID/显示名。
- **玩家数据用 JSON**：不把 `ResourceSaver` 写出的 Resource 放进 `user://` 再 `load()`。JSON 可读、可手改排查，也不会因为脚本类变化而整份存档打不开。
- **不存场景配置**：容器尺寸、`avilable_types`、`vessel_kind`、`max_items` 由场景/代码决定，旧存档不能反向覆盖新配置。
- **不依赖 GBIS 自带存档**：`GBIS.save()` 写 `res://Saves/` 且序列化整个仓库；游戏层只用 `ContainerData` 的公开读写接口。
- **职责分层**：`SaveManager` 只是持久化门面；磁盘 IO 在 `SaveStorage`，去抖/心跳在 `SaveScheduler`，顶层 schema/版本/迁移在 `SaveDocument`，各数据域实现 `SaveParticipant`。会话阶段、活动角色和面锁定在 `GameFlow`，见 `架构/开局流程.md`。

## 2. 组成与文件结构

```text
SaveManager（Autoload 持久化门面）
├─ SaveStorage                 六槽磁盘读写 / 备份轮换 / 只读态
├─ SaveScheduler               脏标记 / 2 秒去抖 / 30 秒心跳
├─ SaveDocument                顶层 schema / 版本 / 迁移
└─ participants（按注册顺序 collect / apply）
   ├─ ContainerSaveParticipant   容器 + detached + orphaned
   └─ CollectionSaveParticipant  见闻

GameFlow（Autoload 会话层，见 架构/开局流程.md）
├─ 当前状态 NO_SESSION / CHARACTER_SELECT / IN_GAME
├─ 活动槽 / 活动角色 / 运行期 PlayerProfile
└─ 调用 SaveManager.create_new_game() / load_slot() / save_now()
```

```json
{
  "version": 2,
  "saved_at_unix": 1793923200,
  "play_time_sec": 3721.5,
  "player": {
	"character_id": "small_coal_lamp",
	"display_name": "小煤灯"
  },
  "containers": {
	"inventory_0": [
	  { "kind": "soul", "id": "<soul_id_1>", "name": "<魂灵名>", "at": [0, 0] },
	  { "kind": "soul", "id": "<soul_id_2>", "name": "<魂灵名>", "at": [5, 0] }
	],
	"vessel_cells": [
	  {
		"kind": "vessel", "id": "<vessel_id>", "name": "<魂器名>", "at": [0, 0],
		"contents": [
		  { "kind": "soul", "id": "<soul_id_3>", "name": "<魂灵名>", "at": [0, 0] }
		]
	  }
	]
  },
  "detached": [
	{ "kind": "soul", "id": "<soul_id_4>", "name": "<魂灵名>" }
  ],
  "collection": {
	"monsters": ["<monster_id>"],
	"souls": ["<soul_id_1>"],
	"vessels": ["<vessel_id>"]
  }
}
```

- `at` 是物品左上角格，形状从资源本身读；`name` 只用于排查，不是读取依据，读档只认 `id`。
- 魂器记录额外带 `contents`：数组格式与容器记录相同，锚点相对魂器内部容器。读档时先按 ID 复制魂器实例，再把内部魂灵放回；魂器内部容器名不存档。
- `detached` 是保存瞬间正在鼠标上的物品；读档时放回仓库第一个空位（`Warehouse.add_item()`），避免丢失。
- 空容器不写入 `containers`；读档时期望容器（仓库页 + 魂器网格）先清空，再按文件重建。商店、装备槽不存。
- 因 mod 缺失/容器满而暂时放不进世界的记录额外写到 `orphaned`：`[{"container": "inventory_0", "record": {...}}]`；没有就不写。
- 写入时 `JSON.stringify(data, "\t")` 排序键，容器记录按锚点排序，见闻 ID 按字母排序，方便 diff。

## 3. 保存时机

| 触发 | 行为 |
|---|---|
| 背包物品增删改、`sig_inv_refresh` | 有活动槽时 `mark_dirty()`，去抖 2 秒后写当前槽 |
| 见闻解锁 `entry_unlocked` | 有活动槽时 `mark_dirty(true)`，下一帧写盘（低频、不可再生） |
| 运行中 | 有活动槽时每 30 秒心跳写一次，刷新 `saved_at` / `play_time` |
| 关闭主窗口 / 应用暂停 | 有活动槽时同步写当前槽 |
| 切档 / 游戏内新游戏 | `GameFlow` 先结束战斗、关面板，再 `SaveManager.save_now()` |
| 新档创建 | `SaveManager.create_new_game()` 写完空文档才算成功 |
| 测试 / 手动 | `SaveManager.save_now()`、`TestAPI.save_now()` |

- 没有活动槽（启动停在 01 面）时 `save_now()` 直接返回 false，不创建任何文件。
- `SaveManager._process()` 每帧只在有活动槽时累计 delta 并交给 `SaveScheduler`；去抖/心跳阈值都在 scheduler 里。不要在信号回调里直接写文件。
- 战斗掉落可能一秒一次，逐次写盘没有必要；`GameFlow` 在切档前会先停战斗，避免旧战斗继续往新档写数据。

## 4. 启动、读档与新建

`SaveManager` 在 autoload 里排在 `CollectionDB`、`SoulRuntimeDB`、`Warehouse` 之后，`GameFlow` 排在 `SaveManager` 之后。`_ready()`：

1. 注册 participants，连接背包/见闻信号；
2. `refresh_slot_summaries()` 扫描六个槽的主文件/备份，只读 `version`、`player`、`saved_at`、`play_time`；
3. `await get_tree().process_frame`：`Warehouse` 预注册 `inventory_0..inventory_9`，`CharacterWindow` 里的 `InventoryView._ready()` 再注册 `vessel_cells`；
4. 检查“期望容器集合”（仓库各页 + 魂器网格）是否全部注册：
   - 没有主场景（`--script`/工具模式）：只读，不读也不写；
   - 主场景存在但缺容器：只读并报错，列出缺失容器名，避免未恢复的容器随后被空数据覆盖；
   - 全部就绪：**不自动读档**，等待 `GameFlow` 选择槽。

`TestAPI.get_save_status()` 可查看 `ready` / `read_only` / `missing_containers` / `active_slot`。

### 4.1 读已有槽

```text
点 01 面存档位
→ GameFlow.request_load_slot(slot)
→ 若已在游戏中：结束战斗、关面板、save_now() 保存当前槽
→ SaveManager.load_slot(slot)
   读主文件 → 失败读 .bak → 都失败：返回 false（空槽不建文件）
   版本高于当前：只读加载
   版本低于当前：SaveDocument.migrate() 并回写
   清空期望容器集合（仓库各页 + 魂器网格）
   按容器、按 at.y / at.x 排序恢复物品；detached 回仓库；见闻按 collection 恢复
   读取 player 段；旧档没有该段时回退默认小煤灯
   emit sig_inv_refresh 一次
→ GameFlow 设置活动角色、状态 IN_GAME、锁 04、解锁 02、翻到 02 面
```

- 不能用 `GBIS.add_item()` 读档：它只找第一个空位，会破坏魂灵左右相邻关系。先 `try_add_to_grid()` 保精确列，失败才兜底。
- 直接操作 `ContainerData` 不逐件发信号，最后发一次 `sig_inv_refresh` 让所有容器视图置脏，可见时再重建。例外是物品放不下时经 `Warehouse.add_item()` 转仓库，这条路径会发 `sig_inv_item_added`。
- `CollectionDB` 在 `_ready()` 就建立 `_seen` 的两个种类桶，`_mark_seen()` 对缺失桶自愈；因此上面那条转仓库路径即使发生在 `apply_save_data()` 之前，魂灵解锁也能正常记录。
- 存档里出现当前未注册的容器时，原始记录逐条转入 `orphaned`，下次写档继续保留，不再直接丢弃。
- 从备份恢复、版本迁移后会自动写回一次；回写沿用该槽的 `.bak`。

### 4.2 新建游戏

```text
04 面点角色
→ GameFlow.create_new_game(character_id)
→ SaveManager.first_empty_slot()
→ SaveManager.create_new_game(slot, {character_id, display_name})
   构造空文档（空容器/见闻 + player 段 + play_time = 0）
   先写盘；失败则保持旧会话和活动槽不变
   写成功后清空内存容器/见闻，设为活动槽
→ GameFlow 设置活动角色、状态 IN_GAME、锁 04、解锁 02、翻到 02 面
```

- 新档使用 `has_disk_data = false` 应用空文档，容器和见闻都回到空状态。
- 满 6 槽时 `GameFlow.request_new_game()` 不建档，只在立方体旁提示「角色已满」。
- 游戏内点「新游戏」会先保存当前槽（只读槽跳过保存并提示）；新角色总是占用下一个空槽，不覆盖有效旧档。
- 文件存在但解析失败的槽按空槽处理；新游戏会覆盖它，旧主文件在写盘时轮换成 `.bak`。

### 4.3 新增持久化域

1. 新建 `XxxSaveParticipant extends SaveParticipant`，实现 `collect_into(document)` 与 `apply_from(document, has_disk_data)`；需要等所有 participant 恢复完再处理的逻辑（例如物品重试入包）放 `finish_load()`。
2. 顶层 section 键加到 `SaveDocument`；如果结构变化需要迁移，在 `SaveDocument.migrate()` 里按版本处理。
3. 在 `SaveManager._ready()` 的 `_participants` 按读档依赖顺序注册。
4. 同步更新本文档；需要测试入口时在 `Scripts/test_api.gd` 补方法。

`player` 段目前由 `SaveManager` 直接维护（`_player_data`），不经过 participant：它在一次会话内不变，不需要每帧收集。

## 5. 物品编码规则

- 魂灵：`kind = "soul"`，`id` 直接用 `ItemData.content_id`（core 和 mod 都由 manifest 写入）。
- 魂器：`kind = "vessel"`，除 `id` 外带 `contents`（内部魂灵记录数组，锚点相对内部容器）。`CollectionDB.get_vessel(id)` 找不到时整件魂器进 `orphaned`；内部某颗魂灵找不到时只保留那条魂灵记录，魂器其余内容正常恢复。
- `content_id` 随 `duplicate()` / `make_instance()` 进入背包副本，所以 mod 内容即使和原版/其他 mod 显示名相同也不会串档。
- 背包里的物品是 `GBIS.add_item()` 复制出来的副本，没有 `resource_path`；`content_id` 随复制保留，读档不需要按名字反查。
- 读档只按 `id` 查；查不到就跳过该物品并 `push_warning`，不会回退到 `name`。
- 新增物品类型时在 `SaveCodec` 加 `kind` 分支，确保能按 ID 找回原资源；不要往存档里塞整份 Resource。

## 6. 见闻

`CollectionDB` 的见闻状态由 `SaveManager` 统一管理：

- `to_save_data()` / `apply_save_data()` 负责序列化和恢复；`apply_save_data()` 结束后发 `state_reloaded`，见闻窗口据此整体刷新；
- 解锁时只发 `entry_unlocked`，由 `SaveManager` 标记立即写盘；
- 存档里没有 `collection` 段时按空状态处理；新档和切档都会先清空见闻。

## 7. 版本、备份与损坏恢复

- `version` 目前是 `2`。v1 没有 `player` 段，`SaveDocument.migrate()` 会补默认小煤灯；旧 `slot_0.json` 自然成为「存档 1」，读档后写回 v2。
- 主文件版本高于当前游戏时只读、不覆盖原文件，避免旧客户端破坏新存档；该槽仍可读取。切档/新游戏时 `GameFlow` 跳过保存并提示「当前存档只读，进度不会保存」，然后继续切换。
- 写盘：先写 `slot_N.json.tmp`，把旧主文件轮换成 `slot_N.json.bak`，再把临时文件改名为主文件。写临时文件失败不会动旧存档。
- 读盘：主文件不存在或 JSON 解析失败时读 `.bak`；从备份恢复后的第一次写盘会保留那份好备份（`_keep_backup_next_save`）。
- `delete_slot(slot)` 删除该槽的三个文件；删除活动槽时会断开活动槽、停止计时、清掉只读态，并由 `GameFlow` 回到 `NO_SESSION`/01 面（停战、关面板）。正常 UI 只能删非活动槽，见 `架构/开局流程.md` §3。
- 备份中仍找不到的 ID、放不下的物品：不丢弃，写进 `orphaned` 并写 warning；写档时原样带回，重新启用 mod 后再读档会尝试放回原容器/仓库。
- `orphaned` 是附加段；没有该段时按空数组处理，`version` 仍为 2。

## 8. 已知边界

- 六槽；启动停在 01 面选档，不自动读档。02/04 的锁定与翻面见 `架构/开局流程.md`。
- 01 面占用槽右上角有删除 ×（第一次点变「确认」，第二次才删）；活动槽不显示删除按钮，主按钮用 ACCENT 绿底标记。`TestAPI.delete_save_slot(slot)` 仍是绕过 UI 的后端直删接口，删活动槽会结束旧会话并回到 01 面。
- 当前可持久化的物品有 `SoulData`（`kind = "soul"`）和 `SoulVesselData`（`kind = "vessel"`）；以后加入其他物品类型时在 `SaveCodec` 补 kind 分支。
- 容器名（`inventory_0..inventory_9`、`vessel_cells`、`shop_0`）变化视为不兼容：旧存档里找不到的容器会 warning 并转入 `orphaned`；下一轮读档会尝试放回原容器或仓库。常量集中在 `Scripts/container_ids.gd`，场景里的 `container_name` 必须与之一致。`--script`/工具模式会在读档前直接返回，不会触发这个跳过逻辑。
- 仓库 10 页各自是独立容器；空页不写入 `containers`，旧存档里的 `inventory_0` 自然成为第 1 页，其余页为空。
- 读档只保证在非战斗、非拖拽状态安全；`GameFlow` 在切档/新游戏前会取消拖拽、发 `session_will_change`，由 `main.gd` 关闭面板并 `BattleWindow.stop_battle()`；只读槽跳过保存。直接调 `SaveManager.load_slot()`（`TestAPI.load_save_slot_raw()`）不会停战斗，测试时自己保证。
- 战斗状态不持久化：切档或关掉游戏再开，从一场新的空战斗开始。
- 主窗口置顶已接入 `user://Settings.cfg`（`Scripts/settings_file.gd`，各业务段自管 key）；面板位置和立方体位置不持久化。音量等其余全局设置还没有接入，也不随新游戏重置。
- 离线收益还没有实现；`saved_at_unix` 已经写进存档，后续做挂机结算只依赖这个时间戳，不存战斗快照。
