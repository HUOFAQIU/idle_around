## 是什么

ADR 记录长期有效的架构决策：当时有什么约束、选了什么、付出什么代价、还考虑过什么。它写「为什么」，不写实现细节；实现细节仍放 `架构/` 或 `指南/`。

spec 是单次改动的契约，改完退出；退出时如果某个取舍会长期约束后续开发，就转成 ADR，而不是留在 spec 或只写进「现状与注意」。

## 何时写

三项同时成立才写：

1. **难逆转**：之后改变主意的成本有意义。
2. **无上下文会意外**：未来读者会问「当时为什么这样做」。
3. **有真实取舍**：存在替代方案，且当时基于具体理由选了这一个。

缺一项就跳过。日常实现细节、临时权衡、能直接从代码读出的结论不写。

## 命名与状态

文件放 `docs/adr/NNNN-<slug>.md`，四位编号递增，slug 用英文短横线。

每份 ADR 标题下先用项目统一文档头，再写决策状态：

```text
> 类型：记录 | 状态：有效 | 核对：YYYY-MM-DD
> 何时读：……
> 关键词：……
> 代码：……
> 相关：……

**决策状态**：已接受 · YYYY-MM-DD
```

决策状态取 `提议` / `已接受` / `已废弃` / `已取代（由 NNNN 取代）`。

## 正文四节

- `背景`：当时的约束、问题，不这么做的代价。
- `决策`：选了什么，边界在哪。
- `后果`：得到什么、付出什么、后续要守什么。
- `替代方案`：考虑过但没选的，为什么不选。

可加 `相关`，链接 spec、其他 ADR 或权威文档。
